# 1. 개요

1.1 시스템개요

CPMS(Contract & Project Management System)는 공사 계약의 의뢰부터 계약품의까지의 과정을
관리하는 시스템이다. 본 매뉴얼이 다루는 범위는 그중 **계약관리 메뉴(bide 모듈)** 이며,
계약의뢰 → 계약사전보고 → 입찰안내 → 현장설명회 → 질의응답 → 입찰 → 평가/업체선정 →
계약품의 순으로 이어지는 업무를 대상으로 한다.

Check Point
1. 예정가 산출·공사비검증·기준정보관리는 별도 모듈(cost)이며 본 매뉴얼의 검증 범위 밖이다.
2. 업체(협력사) 사용자가 사용하는 화면 중 일부는 bidd 모듈에서 제공한다. 부록 B-6 참조.

※ 소스 미확인 — 시스템 전체 구성(서버, 연계 시스템 등)은 소스에 근거가 없어
  이전 매뉴얼 내용을 유지한다.

1. 같은 화면이 **MiPlatform 버전과 RealGrid 버전 두 벌**로 존재한다. URL의 `/mip/` 와
   `/real/` 로 구분되며, 조회 쿼리도 서로 다르다(RealGrid 쪽은 구문 id 끝에 Rg 가 붙는다).
   화면을 분석하거나 문의할 때는 반드시 어느 쪽인지 먼저 확인해야 한다.
2. 계약의뢰서 List만 URL이 하나이고 `mipYn=Y` 파라미터로 갈린다. 파라미터가 없으면

5. '입찰대상 공사관리'와 '현장설명서 템플릿'은 소스에는 있으나 이전 매뉴얼 목차에 없다
   (부록 A 12 참조). 메뉴 노출 여부 확인 필요.
6. 상세 팝업으로 contCompReportDetail.do / contMonthReportDetail.do 가 별도로 있다.

1.4 CPMS ~ KNOX PORTAL 결재 연계 PROCESS

계약관리의 각 문서(계약의뢰서, 계약사전보고, 현장설명회 결과, 계약품의 등)는 화면에서
[Submit] 버튼으로 결재를 상신하고, 결재 결과가 문서의 진행상태(APPROVAL_STATUS)로 반영된다.

진행상태 값은 모든 문서가 공통으로 다음 5가지를 사용한다.

| 값 | 화면 표기 | 의미 |
|---|---|---|
| SAVED     | 작성중   | 저장만 된 상태. 수정·삭제·상신 가능 |
| INPROCESS | 결재중   | 상신됨. 화면의 입력·버튼이 모두 잠긴다 |
| COMPLETED | 결재완료 | 다음 단계로 진행. 되돌릴 수 없다 |
| REJECTED  | 결재반려 | 다시 수정·상신 가능 |
| CANCELLED | 상신취소 | 다시 수정·상신 가능 |

Check Point
1. 결재중(INPROCESS)·결재완료(COMPLETED) 상태에서는 저장/삭제/상신 버튼이 **하나도 나오지
   않는다.** 각 등록 화면의 버튼 조건이 `null·SAVED·REJECTED·CANCELLED` 4개 상태로 통일되어 있다.
2. 상신취소(CANCELLED)나 결재반려(REJECTED)를 받으면 작성중과 동일하게 다시 수정할 수 있다.
3. KNOX 결재함에서 문서를 열면 등록 화면과 다른 **결재 전용 URL**로 진입한다. 화면 이름 뒤에
   A 가 붙는다(bidApprRegistA.do / contApprRegistA.do / evalResultA.do).
4. 문서를 여는 순간의 결재 상태는 공통 프레임워크 테이블(TH_CF_APPROVAL)에서 읽는다.

1.5 계약 일반

(1) 계약의뢰유형
계약의뢰서에서 선택하는 업체선정방식(CONT_REQ_TYPE_CD, 코드타입 BIDE_TYPE)은 3가지이며,
이후 진행 경로가 완전히 달라진다.

| 코드 | 명칭 | 결재완료 후 경로 |
|---|---|---|
| BID | 입찰   | 계약사전보고 → 입찰안내 → 현장설명회 → 질의응답 → 입찰 → 평가/업체선정 → 계약품의 |
| FC  | 수의   | 사전보고·입찰 단계를 **건너뛰고** 곧바로 계약품의 |
| CNG | 변경   | 〃 |

Check Point
1. 계약사전보고 List 조회 쿼리에 `CONT_REQ_TYPE_CD = 'BID'` 가 하드코딩되어 있다.
   따라서 수의(FC)·변경(CNG) 건은 계약사전보고 목록에 **절대 나오지 않는다.**
2. 같은 이유로 검색폼 '계약형태'에서 수의/변경을 선택하면 조건이 충돌해 항상 0건이 조회된다.
3. 수의·변경은 계약의뢰 결재가 완료되면 곧바로 계약품의 대상이 된다.

1.6 사용자 역할 및 권한

(1) 사용자 역할 구분
CPMS의 화면 및 버튼은 로그인 사용자의 역할(Role)에 따라 조회 범위와 활성화 여부가 결정된다.
계약관리(bide)의 역할은 **부여 방식이 서로 다른 3개 계층**으로 되어 있다. 이 셋을 섞어서
"역할"이라고 부르면 혼동이 생기므로 아래와 같이 구분한다.

[계층 1] 시스템 역할 — 역할관리(TN_CF_ROLE)에 등록하고 사용자에게 부여한다.
         계약관리 소스 전체에서 사용하는 역할명은 다음 3개뿐이다.
  R1. Samsung_Semi              : 삼성전자 임직원
  R2. Samsung_Semi_Purchase     : 구매(계약)부서 = 매뉴얼의 "계약진행자"
  R3. Samsung_Semi_Contract_View: 계약 조회 전용
  ※ 소속회사코드(TN_CF_USER.COMP_CODE)가 'C10' 이면 R1 이 없어도 삼성전자 임직원으로 인식한다.
     일부 화면은 C10 만으로 R2(구매부서)까지 인정한다.

[계층 2] 업무그룹 — 업무그룹관리(TN_CF_WORK_GROUP)에 등록한다. 계약관리에서 쓰는 것은 1개뿐이다.
  G1. CONTAPPR_ADMIN            : 계약품의 관리자

[계층 3] 건별 지정 담당자 — 역할을 부여하는 것이 아니라, 문서에 사람을 지정한다.
         지정된 사람만 해당 건에서 특정 버튼·항목을 볼 수 있다.
  P1. 기술평가위원 4종 (계약의뢰서에서 지정, BIDE_CONT_REQ_MST)
        CST_EVAL_INCHARGE_ID  공사수행능력 평가위원
        PC_EVAL_INCHARGE_ID   공정관리 평가위원
        QA_EVAL_INCHARGE_ID   품질관리 평가위원
        SE_EVAL_INCHARGE_ID   안전환경 평가위원
  P2. 환경안전 평가위원 : **설정파일에 지정된 계정 1개**. 건별 지정이 아니다.
        config.properties 의 identity.user.bideBidAppr.agree.id 와 로그인 ID가 같아야 한다.
        (컬럼 ENV_EVAL_INCHARGE_ID 도 존재하나, 평가 점수 조회 권한 판정은 설정값으로 한다.)
  P3. 현장설명서 검토담당자 : 현장설명서 등록 화면에서 검토항목별로 지정한다.
        BIDE_PRESENT_REVIEW.REVIEW_INCHARGE_ID  검토자
        BIDE_PRESENT_REVIEW.REVIEW_CC_ID        참조(부서장)
        검토항목(REVIEW_TYPE_CD) 5종 : BUI(시공) / PRE(기성) / SEQ(보안) / ENV(환경) / LAW(법무)
  P4. 업체담당자 : 업체정보(BIDD_COMPANY)에 입찰담당자(BIDD_INCHARGE_ID)로 지정된 협력사 사용자.
  P5. 등록자 본인 : 각 문서의 FIRST_REG_ID. 거의 모든 화면에서 수정 권한의 기준이 된다.

계약의뢰 화면은 위 R1~R3 을 조합해 3값 코드 하나로 요약한다.
  PUR : Samsung_Semi_Purchase 보유            → 구매(계약)부서
  INQ : Samsung_Semi_Contract_View 보유       → 조회 전용
  REQ : 둘 다 없음(기본값)                     → 의뢰부서(운영부서)

Check Point
1. 소속회사코드가 삼성전자(C10)인 사용자는 Samsung_Semi 역할이 없어도 삼성전자 임직원으로 인식한다.
2. 한 사용자가 복수의 역할을 동시에 가질 수 있으며, 화면별로 요구하는 역할이 다르다.
3. 역할이 조회되지 않는 사용자는 DENY로 처리되어 업체 사용자와 동일하게 취급된다.
4. 계층 3(건별 지정 담당자)은 역할관리 화면에서 부여할 수 없다. 해당 문서를 먼저 등록하고
   그 안에서 사람을 지정해야 생기므로, 테스트 시 "역할을 줬는데 버튼이 안 나온다"의 원인이 된다.
5. 환경안전 평가위원은 설정파일에 박힌 계정 1개뿐이므로, 다른 계정에 역할을 부여해도

3. 결재가 완료되면 계약형태에 따라 다음 화면으로 넘어간다(1.5 (1) 참조).

# 4. 현장설명서 검토담당자

이 장은 계약진행자가 등록한 현장설명서를 **검토**하도록 지정된 사용자를 위한 것이다.
역할관리에서 부여하는 권한이 아니라, 계약진행자가 현장설명서 등록 화면에서 검토항목별로

  검토자   (REVIEW_INCHARGE_ID) : 검토 진행상태와 검토결과를 **입력**할 수 있다.
  참조/부서장(REVIEW_CC_ID)     : 목록에서 해당 건을 **조회만** 할 수 있다. 입력은 불가하다.

검토항목(REVIEW_TYPE_CD)은 시공(BUI) / 기성(PRE) / 보안(SEQ) / 환경(ENV) / 법무(LAW) 5종이며,
항목마다 검토자와 참조를 따로 지정한다.

(계약진행자와 같은 메뉴를 사용한다. 별도의 검토자 전용 메뉴는 없다.)

# 6. 환경안전 평가위원

이 장은 **환경안전 평가만** 담당하는 사용자를 위한 것이다. 기술평가위원과 달리 계약의뢰서에서
사람을 지정하는 방식이 아니라, **서버 설정파일(config.properties)의
`identity.user.bideBidAppr.agree.id` 에 등록된 계정 1개**만이 이 역할을 수행한다.
로그인 ID가 그 값과 정확히 같아야 하며, 다르면 평가 아이콘 자체가 나타나지 않는다.

# 9. 신규업체 등록 프로세스
9.1 신규업체 등록 사유
1. 기존 협력사보다 품질, 가격, 납기 측면에서 우수하다고 판정된 경우
2. 현업 검토 결과, 기존 협력사에서 제조, 납품 불가로 판정된 경우
3. 분사, 합병 등으로 기존 협력사가 존재하면서 별도의 회사가 설립된 경우
4. 당사의 일시적인 필요성 및 협업의 요구에 의해 등록이 필요한 경우
9.2 기본등록조건
1. 재무/기술/환경안전 관련 7개 항목에 대해 기준을 만족한 업체에 한하여 등록이 가능
Check Point
1. 등록자격요건 검토결과 미달항목이 있는 경우 예외등록사유서 작성 및 Knox결재필요
- 전결규정 : [기안] 현업담당자, [결재]현업임원, [통보]구매담당자
2. 환경안전항목(면허/인허가, 환경안전사전평가) 미달시에는 신규등록불가

※ 9장은 시스템 화면이 아닌 사내 업무 프로세스 규정이므로 별도 소스 근거 없음.


9.3 등록프로세스
(1) 신규협력사 등록프로세스
협력사 발굴 단계에서는 요청부서/계약부서 협업으로 진행
   * 신규협력사의 업무에 따라 발굴단계에서 1.5 (2)의 계약담당자와 협업 진행
2. 요청부서에서 발굴된 업체에 대한 등록자격요건 7개 필수항목에 대해 사전 검토
   * 필수항목 불만족 시 예외등록사유서 작성 및 요청부서(임원)결제 필요
     단, 필수항목 중 면허/인허가, 환경안전평가 기준미달시 등록불가
3. 요청부서에서 신규업체등록의뢰서를 작성하고 Knox품의 진행
- 품의시 ‘업무위탁계획서’, ‘환경안전평가결과’, ‘신규업체보안평가요청서’,‘예외등록사유서결제본(해당시)’ 첨부
  * ‘환경안전평가결과’는 각 사업부의 환경안전부서에 의뢰를 진행하여 사전에 결과를 접수 필요
- 결재 전결규정 : [기안] 현업담당자, [결재]현업팀장, [통보]구매담당자

B-6. bide 화면이 bidd 모듈을 호출하는 구간 (2026-08-25 확인)

본 저장소에는 bide 모듈만 반입되어 있으나, bide JSP 6개가 /cpms/bidd/ 경로를
직접 호출한다. 호출되는 URL 은 총 18개다.

  호출하는 JSP
  - biddMgmt/biddRegist.jsp
  - evalMgmt/evalResult.jsp
  - mip/noticeList.jsp
  - mip/qnaList.jsp
  - noticeMgmt/prtcptRegist.jsp
  - presentResultMgmt/presentResultList.jsp

18개 중 14개는 bide 컨트롤러에도 같은 이름의 매핑이 있다(기능이 양쪽에 중복 존재).
나머지 4개는 bide 에 대응 매핑이 없다:

  - /cpms/bidd/evalMgmt/saveEvalResult.do     ← evalResult.jsp:385  [Save]
  - /cpms/bidd/evalMgmt/submitEvalResult.do   ← evalResult.jsp:528  [Submit]
  - /cpms/bidd/evalMgmt/modalBiddNoti.do      ← evalResult.jsp:331  입찰통보 모달
  - /cpms/bidd/noticeMgmt/noticeRegist.do     ← mip/noticeList.jsp:255  [등록]

  (BideEvalMgmtController 전체 매핑 확인 결과 위 3개 이름은 존재하지 않는다.
   evalScoreSave.do / resultReWrite.do 등 다른 이름만 있음)

시사점
- 입찰결과 화면의 [Save]·[Submit] 이 bidd 로 가므로, 이 기능이 운영에서 동작한다면
  bidd 모듈은 배포되어 있는 것이다. 반대로 bidd 가 없다면 두 버튼은 404 가 된다.
  둘 중 어느 쪽인지는 이 저장소만으로 판정할 수 없다.
- 따라서 bide JSP 의 bidd 호출을 '구 경로 잔존 코드'로 단정하면 안 된다.
- 테스트 중 특정 버튼만 아무 반응이 없거나 404 가 난다면 위 4개를 먼저 의심한다.
